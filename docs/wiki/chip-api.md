# CHIP API calls

Every call we make to CHIP, every webhook CHIP makes to us, and what keeps each one from happening twice. The money flows built on these calls are in [payment-flow.md](./payment-flow.md), [refund-flow.md](./refund-flow.md), [payout-flow.md](./payout-flow.md) and [prize-flow.md](./prize-flow.md). The webhooks are covered in detail in [chip-webhook.md](./chip-webhook.md), and the client design decisions in [ADR 0025](../adr/0025-chip-clients.md).

CHIP's sources: the [Collect](https://docs.chip-in.asia/openapi/chip-collect.yaml) and [Send](https://docs.chip-in.asia/openapi/chip-send.yaml) OpenAPI documents, and the [index](https://docs.chip-in.asia/llms.txt) of the rendered docs.

## CHIP Collect (money in)

Every call goes through `chipCollectRequest` (`src/services/chip/chip.ts`), against `https://gate.chip-in.asia/api/v1` with `Authorization: Bearer CHIP_API_KEY`.

| Function             | Endpoint                       | Called from                                                                                                                                                                                                       | `Idempotency-Key`                                  | `reference`                                                                               |
| -------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `createChipPurchase` | `POST /purchases/`             | Checkout (`initiateChipPayment` in `tournaments/[slug]/checkout/route.ts`). Sponsor prize-funding links (`createLink` in `src/services/prizes/funding-requests.ts`).                                              | A random UUID per call. Never stored.              | `payments.id` or `prize_fundings.id`. Used to match webhooks to rows, not to deduplicate. |
| `cancelChipPurchase` | `POST /purchases/{id}/cancel/` | Checkout cancels the previous attempt's purchase before starting a new one (best effort: a failure is logged and ignored). Funding cancels the purchases of removed sponsors, and a purchase it failed to record. | A random UUID per call                             | —                                                                                         |
| `refundChipPurchase` | `POST /purchases/{id}/refund/` | `fireRefund` (`src/services/refunds/fire.ts`), from the refund sweep or an admin's **Retry refund**                                                                                                               | A random UUID per call, so a new key on every fire | —                                                                                         |
| `getChipPurchase`    | `GET /purchases/{id}/`         | The register page's return check (`resolvePaymentState`). A refund re-fire, which reads the purchase before sending again.                                                                                        | None, because reads don't need one                 | —                                                                                         |

**Retries within a call.** These follow CHIP's [errors page](https://docs.chip-in.asia/chip-collect/overview/errors):

| CHIP's answer                 | What `chipCollectRequest` does                                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Network failure, `500`, `503` | Retries with the **same** key, up to 3 attempts in all, about 250 ms and then 750 ms apart, with ±25% jitter.                  |
| `429`                         | Waits out `Retry-After` if it's at most 2 seconds, or backs off as above when there's no header. A longer wait fails the call. |
| `502`                         | Fails at once. CHIP says to wait for the webhook, because the bank or card network may still complete the payment.             |
| Any other `4xx`               | Fails at once.                                                                                                                 |

**Why the key lasts for one call.** CHIP replays the first result for a key. A key kept per refund would replay a `400 purchase_refund_error` forever, when the refund is meant to be retried on the same row. So the key protects against a lost response inside one call, and our own guards handle repeats across calls:

- **Checkout:** one immutable `payments` row per attempt, and a settle that leaves a row that's already `paid` untouched.
- **Refunds:** the `claim_refund_fire` lock, and a re-fire reads the purchase at CHIP before posting again.
- **Funding links:** the record step only writes a row that has no link yet.

**When a call still fails:**

- **Checkout:** the player gets `503 PAYMENT_GATEWAY_ERROR` and can try again.
- **Funding links:** retried on the next funding sync.
- **Cancels:** not retried.
- **Refunds:** the refund stays `pending`. The sweep fires each refund only once, and a refund still pending 15 minutes later (`REFUND_STUCK_AFTER_MINUTES`) appears on `/admin/refunds` for a manual retry.

## CHIP Send (money out)

Every call goes through `chipSendRequest` (`src/services/chip/send.ts`), against `CHIP_SEND_API_URL` with three headers: the bearer key, `epoch`, and a `checksum` recomputed for every request.

CHIP Send documents no idempotency header, so **every Send call is a single attempt**. Duplicates are prevented by `reference` and by our own claims, and retries come from the daily run (`/api/v1/cron/payouts`, 01:00 UTC).

| Function                      | Endpoint                                               | Called from                                                                                                                                                                                                                                              | What stops a duplicate                                                                                                                                                                  | When it fails                                                                                                                                                                                                                                                         |
| ----------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getChipSendAccounts`         | `GET /send/accounts`                                   | Balance check before each payout or prize send                                                                                                                                                                                                           | —                                                                                                                                                                                       | The row stays pending until the daily run.                                                                                                                                                                                                                            |
| `increaseChipSendLimit`       | `POST /send/send_limits`                               | When the balance is below the amount plus the RM1 fee                                                                                                                                                                                                    | `chip_send_limit_id` is stored, and no new request is made while that one is pending. An expired one is replaced.                                                                       | The row stays pending until the daily run.                                                                                                                                                                                                                            |
| `getChipSendLimit`            | `GET /send/send_limits/{id}`                           | Re-checks a stored budget request                                                                                                                                                                                                                        | —                                                                                                                                                                                       | Treated as still waiting.                                                                                                                                                                                                                                             |
| `registerChipBankAccount`     | `POST /send/bank_accounts`                             | After an organization is approved or saves its account (after the response). When a prize is sent to a winner whose account isn't registered yet (`registerPlayerBankAccount`). The daily run, for organization accounts still pending after 15 minutes. | `reference` is our bank account row id. CHIP documents it as a "unique value used to prevent duplicate submissions", and a repeat returns the existing record.                          | The account stays `pending`, and the daily run registers it again.                                                                                                                                                                                                    |
| `createChipSendInstruction`   | `POST /send/send_instructions`                         | `executePayout` and `executePrizeAward`, after `claim_payout_send` or the award claim                                                                                                                                                                    | The claim, which is the point of commitment, and `reference`, which is `payouts.id` or `prize_awards.id`. See [the open question](#open-question-repeated-send-instruction-references). | Insufficient balance (`403`, or the sandbox's `400`) releases the claim and requests budget. `401` and `429` release the claim. Any other `4xx` fails the payout or award for good. `408`, `5xx` and network failures leave it `processing` for the stuck reconciler. |
| `getChipSendInstruction`      | `GET /send/send_instructions/{id}`                     | The stuck reconciler, for rows `processing` longer than `PAYOUT_STUCK_HOURS` (24)                                                                                                                                                                        | —                                                                                                                                                                                       | Tried again on the next daily run.                                                                                                                                                                                                                                    |

CHIP Send's [rate limits](https://docs.chip-in.asia/chip-send/api-reference/rate-limits) are per key, per 5 minutes: 100 send instructions, 60 bank account registrations, 60 budget requests, and 300 for everything else. A `429` waits for the next run.

### Open question: repeated send instruction references

After a timeout or `5xx` on a send, the stuck reconciler resumes the payout or award, which posts the same `reference` again. This flow assumes CHIP then returns the instruction it already has. **CHIP doesn't document that.** Its test integration page says only that an instruction's "reference must be unique". Its OpenAPI document describes the field as "Can be any value", and the uniqueness promise covers only bank accounts. If CHIP answers a repeat with a `4xx` instead, the resume path would mark a payout that was actually sent as failed, because every `4xx` other than insufficient balance, `401` and `429` is final.

Confirm it once in the Send sandbox: post the same reference twice and record the answer here. Until then, treat a `failed` payout or award whose `failure_reason` is `chip_send_4xx` with a duplicate-reference message as possibly paid, and check it in the CHIP portal.

## Webhooks (CHIP to us)

| Route                             | Signature                                                                    | Our answer                                                                                                                  | CHIP's retries                                | Duplicates                                                                                                                                           |
| --------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/v1/webhooks/chip`      | RSA over SHA-256 with the webhook's key, `CHIP_WEBHOOK_PUBLIC_KEY`           | Bad signature: `401`. Database failure: `500`. Anything else, including events we don't use: `200`.                         | Up to 8 attempts over 36 hours 26 minutes     | No key. The settle functions are idempotent: an already-paid payment is untouched, a settled refund is a no-op, and `chip_transaction_id` is unique. |
| `POST /api/v1/webhooks/chip/send` | RSA over SHA-512 with that webhook's own key, `CHIP_SEND_WEBHOOK_PUBLIC_KEY` | Bad signature: `200`, ignored and logged. Missing or unparseable key: `500`. Database failure: `500`. Anything else: `200`. | 25 attempts over about 21 days, then an email | Settlement keeps the first final verdict. Deliveries are matched by `reference`, then by CHIP's id.                                                  |

We don't use CHIP Collect's `success_callback`. It's signed with a different key, and the `purchase.paid` webhook already covers it.

## Known gaps

- **Collect keys protect one call.** A double-submitted checkout or a crash between calls isn't covered by the key, only by the guards above. Keying checkout on `payments.id` would cover it, since each attempt has its own row. How long CHIP keeps a key isn't documented.
- **Send calls are never retried at once.** A network failure during a send leaves the row `processing` until the 24-hour reconciler, because without an idempotency header an immediate retry is only safe if the open question above resolves in our favour.
- **Neither client has a timeout.** A hung CHIP call holds its caller until the platform's own limit.
